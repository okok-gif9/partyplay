# PartyPlay professional redesign — outcome checklist

Native Manus ToDo is not exposed in this session; this project checklist preserves the concrete requested behavior. Existing code already supplies some criteria noted in the implementation plan. Do not mark a criterion complete based on a visual mock-up alone. Production verification found that the connected Supabase MCP project is named `Real` and exposes no PartyPlay `pp_*` schema or migrations, so its database was left untouched; public room discovery and any backend-dependent outcomes remain open until the correct PartyPlay database is connected.

## 1. Guest-first game platform shell and primary navigation
- [ ] PartyPlay is browser-first: users can discover games quickly, start a game in seconds, create private rooms, join rooms with short room codes, play with friends, find public games, match with other players, chat/react inside rooms, track gaming history/statistics, earn achievements, reconnect after temporary connection loss, play comfortably on mobile/desktop, switch between English and Persian, and use the platform for basic quick play without being forced to create an account.
- [ ] The primary navigation is Play, Games, Rooms, Friends, Profile. Secondary navigation/settings can contain Activity, Groups, Game History, Achievements, Settings, Help/How It Works, Report/Safety, About; do not expose every secondary feature in primary navigation.
- [ ] Desktop header contains PartyPlay logo, primary navigation, Search, language switcher, theme control, notifications, profile/avatar, and optional Create Room CTA. Mobile header prioritizes Logo, Search/compact search, Notifications and Profile; mobile navigation provides Play, Games, Rooms, Friends and Profile.
- [ ] Account creation is optional for basic play. Quick Play accepts a display name and supports joining/creating a room without a mandatory account where backend authorization permits. Account paths support sign-up, sign-in, password reset, email verification and social login only if technically enabled; explain accounts save friends, statistics, achievements, game history and preferences.

## 2. Play home and quick-start flows
- [ ] Home sections include a clear PartyPlay identity/value proposition; Create Room, Join Room and optional Quick Play; featured game artwork/title/description/player count/duration/tags/Play; Popular/Trending Games; Quick Games under approximately 5–10 minutes; games grouped by 2, 3–4, 5–8 and 9+ players; Friends Online with avatar/status/invite; Live Public Rooms with game/player capacity/join; Recently Played with result/rematch; recommendations only when enough user data exists.
- [ ] Home hierarchy is 1) PLAY NOW, 2) CREATE/JOIN ROOM, 3) FEATURED GAME, 4) TRENDING, 5) QUICK GAMES, 6) FRIENDS ONLINE, 7) LIVE ROOMS, 8) RECENT GAMES, 9) MORE GAMES. Do not bury the primary action beneath decorative content or overload the home page.
- [ ] A first-time user understands the product within seconds; returning users can start a game within a few clicks. Primary user intents are “I want to play now,” “create a room,” “join my friend’s room,” “find random players,” “see what games exist,” “invite my friends,” and “play again.”

## 3. Game catalog, discovery, details and game engine contract
- [ ] `/games` supports search, categories, tags, player-count, duration, game-mode, online/offline/bot-availability and relevant difficulty filters; sorting includes Popular, New, Recommended, Shortest and Most played.
- [ ] Every game card shows high-quality unique artwork, title, one-line description, player range, duration, tags/category, online status, favorite action when authenticated and a Play action. Difficulty/popularity/new badge are optional; do not show too many badges. Do not use simple Unicode symbols as main artwork or hard-code game metadata throughout UI components.
- [ ] `/games/:gameId` includes hero artwork, title/description, how to play, player range, average duration, difficulty, modes, online availability, supported bot/solo mode, rules/tutorial, visual previews, favorite, Play Now, Create Private Room and Find Public Game; show recent player statistics only where data exists. Provide a clear first-game “How to Play” flow.
- [ ] Maintain a normalized central game registry with id, slug, title, description, shortDescription, artwork, thumbnail, icon, category, tags, min/max players, estimated duration, difficulty, modes, online/bot/spectator availability, status/version, rules and creation/update timestamps as applicable.
- [ ] Each game engine follows a reusable contract for metadata, lobby configuration, initial state, player actions, validation, transitions, serialization/deserialization, win condition, scoring, result generation, reconnect state and game-specific UI. The platform shell does not understand game-specific rules. Prefer a smaller number of polished, fully playable games over unfinished ones.
- [ ] Do not advertise a game as playable without a quality bar. Prioritize Mafia, Spyfall, Tic-Tac-Toe and Connect Four; later candidates are Codenames-style word game, Draw & Guess, Ludo and card game. Use only fitting categories: Party, Strategy, Cards, Word, Drawing, Social Deduction, Quick Games, Two Player, Family Friendly, Competitive.

## 4. Room creation, joining, directory and lobby
- [ ] `/rooms/create` selects a game and supports Public/Private, room name, maximum players, spectators, late joining, chat, family-friendly mode where relevant, game-specific settings and optional password; creating immediately shows the room lobby.
- [ ] `/join` provides a large room-code input, paste support and Join action; it communicates invalid-code, loading, expired-room, full-room and private-room/password states.
- [ ] `/rooms` provides a live (not stale) room list showing game, current/max players, visibility, host, status, Join/Watch action, game/player-count filters, search and refresh/live updates.
- [ ] `/room/:roomId` displays game/art, room code, share/invite, player list, host, ready state/count, audience count if enabled, chat/reactions, game settings, host controls, Start Game and Leave Room. Host controls include Start, Restart, End room, Transfer host, Kick, Mute, Block/Report and Change settings; player controls include Ready/unready, Leave, Report, Block and Invite; spectators can join/leave audience and do not receive hidden information.
- [ ] Room state is explicit: WAITING, READY, STARTING, IN_GAME, PAUSED, FINISHED, CLOSED, EXPIRED; validate transitions (including WAITING→READY→STARTING→IN_GAME, IN_GAME↔PAUSED, IN_GAME→FINISHED→CLOSED), handle unexpected disconnects and do not model lifecycle only with unrelated booleans.

## 5. Quick play, matchmaking and game lifecycle/results
- [ ] `/play` supports preferred game or Any Game, player-count preference, duration/category preference and Find Match. States are Idle, Searching, Match Found, Joining, Failed and Cancelled. While searching, say “You are looking for a 3–8 player party game” (with actual preferences) and expose Cancel; never leave users unsure whether matchmaking is active.
- [ ] Matchmaking considers game, player count, region/latency if available, skill/rank only for ranked modes, party/friend grouping, user preferences and queue time; do not invent ranked casual play.
- [ ] `/game/:sessionId` has appropriate player list, turn/status, timer, connection indicator, chat/reactions, leave/quit confirmation, reconnect state and accessibility controls. Each game has real state transitions, server-authoritative state where needed, anti-cheat/input validation/synchronization and reconnect recovery. Do not trust the client for hidden roles/cards/locations, official scores, winner determination or critical transitions.
- [ ] `/game/:sessionId/results` includes winner/result, scoreboard, player performance, genuinely earned achievements, useful XP/progression only if implemented, Rematch with the same players, New Game, Back to Lobby and share result where appropriate. Primary action is REMATCH; secondary is NEW GAME.
- [ ] End-to-end flows: Quick Game Home→Quick Play→Select game→Find match→Match found→Lobby→Game→Results→Rematch; Private Friend Game Home→Create Room→Select game→Private Room→Copy code→Friends join→Lobby→Start→Game→Results→Rematch; Join by Code Home→Join Room→Enter code→Join→Lobby→Game; Public Room Home→Rooms→Filter→Select room→Join→Lobby→Game; Friend Invite Friends→Select friend→Invite→friend receives notification→Accept→Room→Game; Reconnect Game→Connection lost→Reconnecting→State restored→Continue game.

## 6. Friends, groups, profiles, progress and social safety
- [ ] Friends page shows online/offline friends, requests, add/search, invite to game, recently played with, remove, block and report; recently played with supports reconnecting socially after a game. Presence states are Online, In lobby, In game, Away and Offline without unnecessary precise activity disclosure.
- [ ] Groups, if retained, support create, members, group games, invite, group room, activity, leave and admin controls; Groups do not compete with Friends in primary navigation.
- [ ] `/profile/:username` is a player identity page with avatar, display name, username, online status, bio/tagline, games played, wins, win rate, favorite/recent games, achievements, statistics, friends count and optional privacy controls. Minimum profile statistics are games played, wins, win rate, favorite game, recent games and achievements.
- [ ] `/profile/history` shows game, date, players, result, score, possible rematch and filters. `/profile/achievements` shows unlocked/locked achievements, progress, categories and details; meaningful examples include First Game, Social Player, Party Starter, Spy Master, Win Streak and Play With New People. Do not create meaningless achievements.
- [ ] Notifications cover friend request/acceptance, game/room invite, group activity, achievement, match and system notice; each has read/unread state, timestamp, relevant action, mark-as-read and clear-all/read-all behavior; avoid spam.
- [ ] Social safety supports private reports and report reasons Harassment, Spam, Offensive content, Cheating and Other; Block, Report, Mute, rate limiting, chat moderation/profanity filtering where appropriate, privacy settings, clear community rules and host controls. Moderator tools remain separate from normal user UI. Do not build a broad public social network unnecessarily.

## 7. Platform architecture, real-time/security and data integrity
- [ ] Use Supabase Realtime/existing infrastructure appropriately and separate auth, profile, social graph, room state, game session state, chat, notifications, statistics and achievements. Avoid unnecessary realtime subscriptions.
- [ ] Suggested data entities are profiles, friendships, friend_requests, blocks, groups, group_members, games, game_sessions, game_session_players, rooms, room_players, room_settings, room_messages, room_events, notifications, game_results, player_game_stats, achievements, player_achievements, game_favorites, matchmaking_queue, reports and moderation_actions.
- [ ] Enforce RLS and per-resource authorization. Input validation, server-side validation for critical game actions, rate limiting/anti-spam, secure sessions, unauthorized-room protection, unauthorized-game-state protection, sanitization of user content, reporting/blocking and safe external links are required. Never expose service-role credentials or trust client-side authorization.
- [ ] Reconnect states are CONNECTED, CONNECTING, RECONNECTING, DISCONNECTED and FAILED. Show “Connection lost. Reconnecting…” and, on failure, “Your connection could not be restored” with a safe recovery path. Restore session/room, resynchronize state, handle timeout and use user-friendly messages.
- [ ] Do not represent unsupported infrastructure as real: server-authoritative hidden information, matchmaking, public room freshness, result persistence, guest room authorization and reconnect need actual backend support. Do not replace existing real game/social data with demo fixtures.

## 8. Settings, localization, accessibility, responsive behavior
- [ ] `/settings` sections include Account (email, username, password, account deletion), Appearance (Light/Dark/System), Language (English/Persian), Privacy (profile visibility, friend requests, online status, invitations), Gameplay (sound, animation, reduced motion, chat preferences), Safety (blocked users, reports, moderation preferences) and Accessibility (text size, contrast, reduced motion, keyboard navigation).
- [ ] All visible UI text—including errors, loading, empty states, notifications, game instructions, validation and system messages—is centralized in EN/FA translation dictionaries. Persian uses correct RTL typography/layout; do not mechanically mirror without checking quality. Use semantic HTML, keyboard navigation, visible focus, necessary ARIA labels, sufficient contrast, reduced motion, screen-reader status announcements, non-color-only state communication and large touch targets.
- [ ] Support small/large phones, tablets, laptops and large monitors; core interactions work by touch without hover-only behavior. Room code is readable and easy to copy/share; keyboard access works on desktop; game boards respond to small screens.
- [ ] Central design tokens cover colors, type, spacing, radius, shadows, z-index, motion, breakpoints and component states; support excellent Light and Dark modes. Design remains clear with all animation disabled. Avoid excessive gradients, glass, neon, shadows and floating decoration.

## 9. Help, errors, sharing, performance and production quality
- [ ] Help/How It Works explains room creation, joining, multiplayer, game rules, account FAQs, connection troubleshooting and safety/reporting.
- [ ] Polished states cover 404, 403, 500, Offline, Maintenance, Room not found, Room expired, Room full, Game unavailable and Session expired. Do not show raw technical/database errors; translate failures into actionable messages.
- [ ] Public pages have proper titles, descriptions, Open Graph, Twitter/X cards where appropriate, canonical URLs and semantic HTML. Shareable pages are game pages, public profiles if enabled, public room invites and suitable results; private rooms never leak through indexing.
- [ ] Consider PWA installability/app icon/splash/offline shell where practical; never claim realtime games work offline. Track product analytics only when actually configured and minimize personal data.
- [ ] Optimize with route-level splitting, lazy games, optimized/responsive artwork, efficient Supabase queries, pagination/virtualization when needed and caching of stable data.
- [ ] Empty lists offer the next action (friends, public rooms, history and notifications); no blank loading screens—use skeleton/progress/contextual text; include actionable errors and success feedback.
- [ ] Before completion verify desktop/mobile, dark/light, English/Persian/RTL, loading/empty/error/success/offline/reconnect, keyboard/touch, slow network, long names, large player lists and very small screens. Preserve working online gameplay.

## 10. Coherent product architecture and delivery
- [ ] Follow a scalable structure: app/router/providers/layouts; components/ui/navigation/game/room/social/profile; features/auth/games/rooms/matchmaking/friends/groups/chat/notifications/achievements/profile; games/mafia/spyfall/tic-tac-toe/connect-four; lib/supabase/realtime/analytics/i18n/validation; hooks/services/stores/types/utils/data/styles. Separate domain logic from presentation; do not make one enormous App.tsx.
- [ ] Separate server state (Supabase, rooms, friends, profiles, notifications), client/UI state (modals, filters, theme, forms) and game state; do not put everything into one global object.
- [ ] Product should feel FAST, SOCIAL, PLAYFUL, POLISHED, TRUSTWORTHY, RESPONSIVE and MODERN—not CORPORATE, CLUTTERED, GENERIC, AI-GENERATED, an admin dashboard or a collection of unfinished demos. Preserve useful existing functionality and prioritize working core multiplayer UX.
- [ ] Before implementation inspect repository, package scripts, routing, Supabase, authentication, games, reusable components, schema assumptions and existing placeholders. Implement incrementally; if a feature cannot be fully implemented with current backend/infrastructure, mark it TODO and specify exactly what backend is needed.
- [ ] Required final experience includes easy game discovery, create/join room, public rooms, synchronized multiplayer, reconnection, lobby controls, tutorials, results/rematch, friend invites, useful profile stats, achievements, notifications, basic chat moderation, mobile UI, dark/light, English/Persian/RTL, polished loading/empty/error states, enforced security, no exposed secret keys and acceptable mobile performance.
